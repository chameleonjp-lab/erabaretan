# 選ばれたん：実装計画書

- 文書状態：初期実装計画版
- 対象：iPhone向け1対1オンライン版
- 更新日：2026-08-09

## 1. この文書の目的

本書は、「選ばれたん」を低い運用費で公開できるオンライン対戦カードゲームとして実装するために、構成、データ、通信、公平性、切断復帰、試験、公開順序を定める。

実装速度だけを優先しない。次の条件を同時に満たすことを目標とする。

- iPhoneで読みやすく、誤操作しにくい。
- 隠された手札と山札順を相手へ漏らさない。
- クライアント改造で体力、得点、カードを変更できない。
- 通信が切れても試合へ戻れる。
- 同じ記録から同じ試合結果を再現できる。
- 利用者が少ない初期段階では、無料枠またはごく低い費用で運用できる。
- 将来の2対2、複数人戦、観戦、リプレイへ拡張できる。

## 3. 通信方式の判断

当初の目的は、P2Pによりサーバー費を抑えることだった。しかし、本作は隠された手札、山札順、乱数、最終評価を扱う。

完全P2Pでは、ホストが次の情報を不正に変更または閲覧できる。

- 自分と相手へ配るカード
- 山札の順番
- 相手の手札
- 世界損傷と回復記録
- 体力と勝敗

そのため、最初の正式版では、プレイヤーとは別の対戦管理処理が正しい状態を決める。

### 3.1 比較

| 方式 | 運用費 | 秘密情報 | 不正耐性 | 切断復帰 | 採用判断 |
|---|---:|---:|---:|---:|---|
| 完全P2P | 最小 | 弱い | 弱い | 弱い | 技術検証または友達専用のみ |
| ホスト権威型P2P | 小さい | ホストに見える | ホスト不正に弱い | ホスト切断で終了しやすい | 正式版では不採用 |
| サーバー権威型WebSocket | 小さい | 守りやすい | 強い | 実装しやすい | **最初の正式版に採用** |
| P2P＋公平な暗号配札 | 小さい | 守れる可能性 | 実装難度が高い | 複雑 | 将来研究のみ |

### 3.2 採用構成

```text
GitHub
  └─ ソースコード、Pull Request、GitHub Actions

Cloudflare Pages
  └─ ゲーム画面、カード画像、音声、静的ファイル

Cloudflare Worker
  └─ ルーム作成、入室、WebSocket接続の入口

Durable Object（1部屋につき1個）
  ├─ 山札と手札
  ├─ 体力と世界耐久
  ├─ 手番と制限時間
  ├─ フィールド効果
  ├─ 個人別の世界損傷・再生
  ├─ 行動記録
  └─ 再接続用の状態
```

1部屋を一つのDurable Objectとして扱う。すべての部屋を一つの大きな処理へ集めない。

静的画面はCloudflare Pagesを第一候補とする。同じCloudflare上で配信と通信入口を管理しやすいためである。GitHub Pagesは静的画面の代替候補として残す。

## 4. なぜDurable Objectsを使うか

本作では、同じ部屋の二人が一つの正しい状態を共有し、同じ瞬間に送られた操作を順番に処理する必要がある。

Durable Objectsは、部屋単位の状態管理、強い整合性、WebSocket、永続化に向いている。Cloudflareの公式資料でも、チャットルームやマルチプレイヤーゲームが用途として挙げられている。

採用時の原則は次のとおりとする。

- 1部屋につき1オブジェクト
- 重要な状態はメモリだけでなく保存する
- WebSocket Hibernation APIを使い、待機中の実行費を抑える
- `setInterval`で常時動かさず、期限は保存時刻とAlarmで処理する
- ルームIDから同じオブジェクトへ到達できるよう決定的に割り当てる
- 対戦終了後は保存期間を決めて削除する

## 7. ルール処理の設計

### 7.1 決定的な処理

同じ初期状態、同じ乱数列、同じ操作列から、必ず同じ結果が出るようにする。

ルール処理の中心は、概念上次の形にする。

```text
現在状態
＋ 検証済み操作
＋ 乱数結果
↓
新しい状態
＋ 公開イベント
＋ 各プレイヤーだけに見せる秘密イベント
```

画面から直接、体力や得点を書き換えない。

### 7.2 処理順を文書化する

カード効果が増える前に、次の順序を固定する。

1. 使用条件を検証
2. 使用カードを手札から除く
3. 攻撃宣言
4. 防御と反応
5. 戦闘ダメージ
6. 追加効果
7. 世界損傷
8. 世界再生
9. 世界境界反応
10. 死亡判定
11. 試合終了判定
12. 暫定評価
13. 補充と次の手番

反射、同時死亡、世界0、回復上限などの例外も、この順序表へ追加する。

### 7.3 イベント記録

状態の変更だけでなく、変更理由を記録する。

```text
MATCH_STARTED
CARD_DRAWN
CARD_PLAYED
DEFENSE_SELECTED
DAMAGE_APPLIED
WORLD_DAMAGED
WORLD_RESTORED
WORLD_THRESHOLD_TRIGGERED
FIELD_REPLACED
PLAYER_DEFEATED
MATCH_ENDED
```

すべてのイベントに次を持たせる。

- `eventId`
- `matchId`
- `eventVersion`
- `sequence`
- `actorPlayerId`
- `round`
- `turn`
- `createdAt`
- 必要な結果データ

イベントの版を残し、カードやルールを変更した後でも過去記録を区別できるようにする。

```text

  ↓
```

## 10. 通信手順

### 10.1 クライアントから送る命令

```text
CREATE_ROOM
JOIN_ROOM
READY
START_MATCH
PLAY_CARD
SELECT_USE_MODE
SELECT_TARGET
SELECT_DEFENSE
ACCEPT_DAMAGE
DISCARD_CARD
SURRENDER
RESUME_SESSION
REQUEST_SNAPSHOT
```

各命令には次を付ける。

- `protocolVersion`
- `matchId`
- `playerId`
- `commandId`
- `expectedSequence`
- `payload`

同じ`commandId`が再送された場合は、二重実行せず前回結果を返す。

### 10.2 サーバーから送る通知

```text
ROOM_CREATED
PLAYER_JOINED
READY_STATE_CHANGED
MATCH_STARTED
PRIVATE_HAND_UPDATED
TURN_STARTED
ACTION_ACCEPTED
ACTION_REJECTED
CARD_REVEALED
DAMAGE_RESOLVED
WORLD_UPDATED
FIELD_UPDATED
SCORE_PREVIEW_UPDATED
RECONNECT_REQUIRED
MATCH_ENDED
```

相手の手札を含む一つの完全状態を全員へ配らない。プレイヤーごとに見せてよい情報だけを作る。

### 10.3 通信量を増やさない

本作はターン制である。位置情報を毎秒送る必要はない。

- 操作があったときだけ送る。
- 時計表示は、サーバーが送った締切時刻から端末側で描画する。
- 毎秒の残り時間をサーバーから送らない。
- 演出の細かい座標や粒子を通信しない。
- まとめられる通知は一つの解決結果にまとめる。

## 11. 山札、乱数、公平性

### 11.1 乱数生成

山札順やルーム用トークンに`Math.random()`を使わない。

サーバー側でWeb Crypto APIを使い、予測しにくい値を作る。

### 11.2 山札の証明

試合開始時に、山札順そのものは公開せず、変更されていないことを後で確認するための値を公開する。

概念：

```text
commitment = SHA-256(
  ruleVersion
  + matchId
  + secretSalt
  + orderedDeck
)
```

試合終了後に、検証用の山札情報とSaltを公開する。開始時の値と一致すれば、試合途中で山札を変更していないことを確認できる。

これはサーバーを完全に不要にする仕組みではない。運営側の処理が途中で山札を変更していないかを、試合後に検証しやすくする補助である。

### 11.3 クライアントを信用しない

サーバーは次を毎回検証する。

- そのプレイヤーの手番か
- 指定カードを実際に持っているか
- 指定した使用方法がカード定義にあるか
- 対象が有効か
- 必要な体力や条件を満たすか
- 防御枚数と反応回数が上限内か
- 世界損傷と得点がサーバー計算と一致するか

クライアントから「ダメージ16」「世界損傷7」という結果を受け取らない。クライアントはカードと選択だけを送り、結果はサーバーが計算する。

## 12. 切断と復帰

### 12.1 再接続情報

入室時に、推測しにくい再接続トークンを発行する。

端末には次だけを保存する。

- `roomId`
- `playerId`
- `resumeToken`
- `lastReceivedSequence`

サーバーにはトークンそのものではなく、検証用のハッシュを保存する。

### 12.2 復帰手順

1. WebSocketが切断される。
2. 画面は即敗北にせず、再接続中と表示する。
3. 同じルームへ`RESUME_SESSION`を送る。
4. サーバーがトークンを確認する。
5. プレイヤー専用の最新状態と不足イベントを返す。
6. 進行中の制限時間へ戻る。

### 12.3 切断中の扱い

- 切断後60秒を基本猶予とする。
- 相手の画面には「再接続待ち」と残り猶予を表示する。
- 一時停止を悪用できないよう、手番時計を完全停止するかは試遊で決める。
- 猶予を超えた場合は切断敗北として神の評価へ進む。
- サーバー障害とプレイヤー切断を可能な範囲で分けて記録する。

## 13. 制限時間とAlarm

Durable Objectでは、部屋ごとに現在の締切時刻を保存する。

- 手番開始時に`deadlineAt`を保存する。
- 必要な期限にAlarmを設定する。
- Alarm発火時に、現在の状態と締切を再確認する。
- すでに行動済みなら何もしない。
- 時間切れなら安全な既定行動を実行する。

一つのDurable Objectで利用できるAlarmは一つとして設計し、複数の期限がある場合は最も近い期限を設定する。

`setInterval`や常時実行する時計を使わない。待機中にDurable Objectが休止できるようにする。

## 14. 保存方針

### 14.1 永続化するもの

- ルーム状態
- 対戦状態
- 山札と手札
- 手番と締切
- フィールド
- 世界責任台帳
- 再接続情報
- イベント列
- 最終結果

重要な状態は、クライアントへ通知する前に保存する。

### 14.2 保存期間

初期案：

- 待機だけで終わった部屋：短期間で削除
- 終了した通常対戦：7〜30日で削除を検討
- 不具合調査用に同意を得た記録：別の管理方法を検討
- 公開ランキング導入前は長期保存しない

保存期間は、実際の調査需要、個人情報、費用を確認して決める。

### 14.3 ログへ残さないもの

本番ログに次をそのまま出さない。

- 再接続トークン
- 完全な秘密手札
- 山札Salt
- 将来のカード順
- 必要のない端末識別情報

## 15. セキュリティ

### 15.1 最低限の対策

- ルームIDとトークンは暗号学的に安全な乱数で作る。
- 受信メッセージの形式、型、長さを検証する。
- 1接続あたりの送信頻度を制限する。
- 1命令の最大サイズを小さく保つ。
- 不正な状態遷移を拒否する。
- すべての操作へ一意なIDを付け、再送を二重実行しない。
- クライアントの時計を勝敗判定に使わない。
- エラー応答で秘密状態を返さない。
- 本番の秘密情報をリポジトリへ保存しない。

### 15.2 放置と嫌がらせ

公開マッチングを入れる段階で、次を追加する。

- 連続時間切れの自動降参
- 同一相手への嫌がらせ再入室防止
- 表示名の禁止文字と長さ制限
- 通報
- 対戦記録による確認

初期の合言葉対戦では、常時チャットを入れず、定型反応だけにする。

## 16. 費用を抑える設計

2026-08-09時点のCloudflare公式料金表では、Durable ObjectsのFree planに1日あたりのリクエスト枠と実行時間枠がある。WebSocketの受信メッセージは一定比率でリクエスト換算され、Hibernation中は実行時間の課金対象外になる。

料金と制限は将来変わり得るため、公開前に必ず公式資料を再確認する。

本作では次により使用量を抑える。

- 1試合1部屋の小さな状態に分ける。
- WebSocket Hibernation APIを使う。
- 毎秒の時計通信をしない。
- 画面演出を端末側で行う。
- 操作と確定結果だけを送る。
- 対戦終了後の部屋を不要に保持しない。
- 画像と音声は静的配信に置く。
- 開発環境と本番環境の保存データを分ける。

### 16.1 公開前の費用確認

次を計測してから、無料枠内の想定人数を計算する。

- 1試合あたりの接続数
- 1試合あたりの受信メッセージ数
- 1試合あたりの保存行数
- 平均試合時間
- 待機部屋の平均保持時間
- 再接続率
- 1日あたりの試合数

「サーバー費0円」を保証として表示しない。初期利用では無料枠内を目標とし、上限接近時に公開範囲や保存量を調整できるようにする。

## 17. 自動試験

### 17.1 単体試験

- 各カードの使用条件
- 攻撃と防御の計算
- 世界損傷と再生
- フィールドの上書きと終了
- 境界反応が一度だけ起きること
- 世界0時の破界責任
- 生存ポイントと最終評価
- 同時死亡
- 手札上限
- 時間切れの既定処理

### 17.2 不変条件

どの操作列でも、次を破らないことを確認する。

- 体力が定義外の値にならない。
- 世界耐久が0未満または上限超過にならない。
- 同じカード実体が二人の手札へ同時に存在しない。
- 山札、手札、使用済みカードの総数が一致する。
- 一度発生した世界境界反応が再発しない。
- 終了した試合へ新しい戦闘操作を適用しない。
- 得点台帳と表示合計が一致する。
- 同じ命令を再送しても一度しか処理しない。

### 17.3 自動対戦

複数の簡単なCPU方針を用意する。

- 生存優先
- 攻撃優先
- 世界保護優先
- 評価最大化
- 無作為

数千〜数万試合を実行し、次を確認する。

- 先攻と後攻の勝率差
- 試合時間
- 世界崩壊率
- 生存者と選定者が異なる率
- 使用されないカード
- 極端に高い勝率のカード
- 回復と防御の循環
- 選べる行動がない手番

自動対戦の勝率だけで面白さを決めない。人間が理解できるか、負けに納得できるかは別に試す。

## 18. ブラウザ試験

最低限、次を確認する。

- iPhone 17 Pro相当のSafari
- iPhone 11 Pro相当のSafari
- iPad Pro 2018相当のSafari
- 小さいiPhone相当の画面幅
- Android Chrome相当
- PCのSafari、Chrome、Edge相当

主な確認項目：

- 縦画面で手札が見切れない。
- 横スクロールが起きない。
- 文字を拡大しても重要操作が消えない。
- 誤タップで即時に危険カードが発動しない。
- バックグラウンド復帰後に再接続できる。
- 音声が再生できない場合も進行する。
- 低速通信で二重操作が起きない。
- 画面ロック、タブ復帰、回線変更後の挙動が明確である。

## 21. 工程ごとの品質門

次の条件を満たさない場合、後続工程へ進まない。

| 品質門 | 条件 |
|---|---|
| ルール | 同じ記録から100％同じ結果を再生できる |
| カード | 使用不能手番と無限循環が基準内 |
| 通信 | 二重送信で二重行動が起きない |
| 秘密情報 | 相手の手札と山札順が通信結果へ含まれない |
| 復帰 | 再読み込み後に本人の手札と正しい手番へ戻れる |
| 採点 | 表示された内訳から合計を説明できる |
| 操作 | 危険カードを確認なしで誤発動しない |
| 費用 | 1試合あたりの通信と保存量を実測している |
| 公開 | 重大な進行停止、不正記録、権利問題が残っていない |

## 22. 主な危険と対策

| 危険 | 影響 | 対策 |
|---|---|---|
| 世界評価が複雑 | 勝敗に納得できない | 暫定評価、原因別内訳、試合記録 |
| クライアント改造 | 不正なカードや得点 | サーバーが全操作を検証し結果を計算 |
| 相手の手札漏えい | 対戦が成立しない | プレイヤー別の状態を生成する |
| 二重送信 | カードを2回使う | commandIdとsequenceで重複排除 |
| Durable Objectの休止 | メモリ状態が消える | 重要状態を保存し、復元できる設計 |
| 手番時計が休止を妨げる | 費用増加 | 端末描画＋Alarm、setInterval不使用 |
| 切断による敗北 | 不満と離脱 | 再接続トークン、猶予、状態再同期 |
| 破壊カードが最適 | 独自性が消える | 世界反応、減点、対抗カード、自動対戦 |
| 回復が最適 | 試合が進まない | 回復コスト、最大ラウンド、回復効率逓減の検討 |
| 無料枠超過 | 対戦不能 | 実測、警告、保存削減、段階公開 |
| 仕様変更で過去記録が壊れる | リプレイ不能 | ruleVersionとeventVersionを保存 |

## 23. P2Pを将来使う場合

WebRTC DataChannelは、ブラウザ同士で任意データを直接送受信できる標準である。

ただし、本作でP2Pを採用する場合は用途を限定する。

候補：

- 公式成績を残さない友達対戦
- 対戦後のリプレイファイル共有
- 定型反応や演出同期
- サーバー停止時の実験モード

P2P版で山札と秘密手札を扱うには、ホストを信用するか、暗号配札を実装する必要がある。正式対戦へ採用する前に、iOS Safariでの接続率、TURN中継の必要率、切断復帰、不正耐性を別工程で検証する。

「P2Pだから必ず無料」とは扱わない。接続仲介やTURN中継が必要になる場合がある。

## 25. 完成の定義

最初の1対1版を「完成」と判断する条件：

- CPU練習と合言葉対戦が動く。
- iPhone縦画面で一試合を完了できる。
- ルール計算を同じ記録から再生できる。
- 相手の秘密手札が漏れない。
- クライアントが送った得点を信用していない。
- 再読み込みまたは一時切断から復帰できる。
- 世界損傷、世界再生、生存の内訳を結果画面で説明できる。
- 世界状態が見た目と音へ反映される。
- 重大な無限循環と進行停止がない。
- 1試合あたりの運用量を計測している。
- 新規プレイヤーが2試合以内に中心ルールを説明できる。
