# 選ばれたん：実装・検証・公開計画書 V2

- 文書状態：現行
- 対象：12種類の最小確認から、48種類の限定公開まで
- 更新日：2026-08-09
- 優先関係：本書と旧版が食い違う場合は本書を採用する

## 1. この文書の目的

本書は、ゲームとしての面白さを確認する前に通信基盤へ作業が偏らないよう、実装、試遊、品質確認、限定公開の順序を定める。

技術的に動くことだけを完成条件にしない。

各段階で、遊ぶ側が感じる価値を確認し、条件を満たさない場合は後続工程へ進まない。

---

## 2. 実装原則

### 2.1 面白さを先に確認する

最初に作るのはオンライン対戦ではない。

12種類のカードを同じ端末で交互に操作し、次の迷いが生まれるかを確認する。

- 強い力を解放するか
- 世界損傷を避けて抑制するか
- 相手を攻撃するか
- 世界を回復するか

この迷いが生まれない場合は、Cloudflare、WebSocket、切断復帰へ進まない。

### 2.2 ルールを画面と通信から分ける

ルール計算は、画面、CPU、通信基盤へ依存させない。

同じ初期状態、乱数、操作列から、必ず同じ結果を出す。

同じ処理を次で使う。

- 同一端末対戦
- CPU戦
- 自動対戦
- オンライン対戦
- リプレイ
- 不具合再現

### 2.3 オンラインではプレイヤー端末を信用しない

正式なオンライン対戦では、次を対戦管理側が決める。

- 山札順
- 手札
- 体力
- 世界耐久
- 世界損傷と世界再生
- 世界反応
- フィールド
- 制限時間
- 最終評価

クライアントは、カードと使い方と対象だけを送る。

### 2.4 作業を細かく分けすぎない

一つのPull Requestで、一つの確認可能な成果物を完成させる。

例：

- 「カード定義だけ」ではなく「12種類で一試合完了できる」
- 「WebSocket接続だけ」ではなく「別端末2台で一試合完了できる」
- 「結果画面の枠だけ」ではなく「選定理由を説明できる」

途中の小さな変更を大量のPull Requestへ分けない。

## 3. 採用する全体構成

### 3.1 面白さ確認まで

```text
ブラウザ
  ├─ ゲーム画面
  ├─ ルール処理
  ├─ CPU
  └─ 試合記録
```

通信を使わない。

### 3.2 オンライン対戦以降

```text
GitHub
  ├─ ソースコード
  ├─ 計画書
  ├─ Pull Request
  └─ GitHub Actions

Cloudflare Pages
  └─ 画面、画像、音、静的ファイル

Cloudflare Worker
  └─ ルーム作成、入室、接続入口

Durable Object：1対戦部屋につき1個
  ├─ 山札と手札
  ├─ 体力と世界耐久
  ├─ 世界責任台帳
  ├─ 手番と期限
  ├─ 世界律とフィールド
  ├─ イベント記録
  └─ 再接続状態
```

1部屋を一つの状態管理単位とする。

すべての対戦を一つのDurable Objectへ集めない。

### 3.3 P2Pの扱い

完全P2Pは、正式結果を保存しない友人対戦の研究候補として残す。

最初の正式版では使わない。

理由：

- ホストが相手の手札を見られる
- 山札を変更できる
- ホスト切断で試合が終わりやすい
- 不正な得点を検出しにくい
- 切断復帰が複雑になる

P2Pを再検討する場合は、正式版と別工程で接続率、TURN中継、不正耐性を確認する。

## 4. 技術構成

### 4.1 画面

- TypeScript
- HTML
- CSS
- Vite
- 通常のHTML要素を中心としたカードと操作
- Canvasは世界背景や粒子など、限定した演出に使う
- Web Audio API
- IndexedDBまたはlocalStorageによる再接続情報保存

画面全体を重いゲームエンジンへ依存させない。

### 4.2 ルール

- 状態を直接書き換えず、操作から新しい状態を作る
- カード効果をデータと処理へ分ける
- 乱数の種と結果を記録する
- ルール版、カード版、イベント版を保存する
- 同じ試合記録を100％再生できるようにする

### 4.3 オンライン

- Cloudflare Workers
- Cloudflare Durable Objects
- WebSocket
- Hibernation WebSocket API
- SQLite-backed Durable Object storage
- Web Crypto API

実装開始時に、Cloudflare公式資料、Wrangler設定、型定義を再確認する。

### 4.4 試験

- Vitest：ルール、採点、カード、状態遷移
- fast-check等：不変条件と予期しない操作列。導入は保守状況を確認して判断
- Playwright：主要画面、再読み込み、再接続
- GitHub Actions：型検査、試験、ビルド
- 自動対戦：数千〜数万試合

## 13. ルール処理

### 13.1 概念

```text
現在状態
+ 検証済み操作
+ 乱数結果
↓
新しい状態
+ 全員へ見せる出来事
+ 本人だけへ見せる出来事
```

### 13.2 基本処理順

1. 操作の形式を検証
2. 手番と状態を検証
3. カード所持を検証
4. 解放、抑制、対象を検証
5. カードを手札から除く
6. 攻撃または介入を宣言
7. 防御または反応を受け付ける
8. 戦闘ダメージを処理
9. 追加効果を処理
10. 世界損傷を処理
11. 世界再生を処理
12. 世界境界反応を処理
13. 体力0と世界0を判定
14. 戦闘結果を判定
15. 神の評価を計算
16. 補充と次の手番

正式版は`RULE_PROCESSING_ORDER.md`で例外まで固定する。

### 13.3 必ず試験する例外

- 同時死亡
- 反射による死亡
- 世界損傷と再生が同時に起きる
- 世界0と相手体力0が同時に起きる
- フィールド上書き時の継続効果
- 最大ラウンド終了時の同点
- 切断中の時間切れ
- 同じ命令の再送

## 16. 山札と公平性

### 16.1 乱数

山札、ルームID、再接続トークンに`Math.random()`を使わない。

Web Crypto APIを使う。

### 16.2 山札の証明

試合開始時に、山札順を隠したまま、後から変更していないことを確認する値を公開する。

試合終了後に検証用情報を公開する。

この機能は、運営側の処理を完全に信用不要にするものではない。

対戦途中で山札を変更していないか確認しやすくする補助とする。

### 16.3 クライアントから受け取らない結果

次をクライアント計算として受け取らない。

- ダメージ値
- 防御後の体力
- 世界損傷
- 世界再生
- 暫定評価
- 最終評価
- 勝敗

## 17. 再接続

### 17.1 端末へ保存するもの

- roomId
- playerId
- resumeToken
- lastReceivedSequence

### 17.2 対戦管理側

再接続トークンそのものではなく、検証用ハッシュを保存する。

### 17.3 復帰手順

1. 切断を検知
2. 再接続中と表示
3. 同じルームへ復帰命令
4. トークンを確認
5. 本人用の最新状態を返す
6. 不足した出来事を返す
7. 現在の期限へ戻る

### 17.4 猶予

初期値は60秒とする。

完全停止を悪用できないよう、手番時計の扱いは試遊で決める。

相手には待機理由と残り猶予を表示する。

- 縦画面で手札が見切れない
- 横スクロールが起きない
- 文字拡大で決定ボタンが消えない
- 危険な解放を誤タップしない
- 長押しやスクロールがカード使用と衝突しない
- バックグラウンド復帰後に戻れる
- 音が再生できなくても進行する
- 回線変更で二重操作が起きない
- 画面ロック後の状態が明確

ユーザーがPCを持たない前提でも確認できるよう、主要な確認項目をGitHub上のチェック表へ残す。

## 22. 費用確認

限定公開前に、次を実測する。

- 1試合の接続数
- 1試合の受信メッセージ数
- 1試合の保存量
- 平均試合時間
- 待機部屋の保持時間
- 再接続率
- 1日あたりの試合数
- 終了部屋の保存期間

使用量を抑える方法：

- WebSocket Hibernation API
- 毎秒の時計送信をしない
- 演出を端末側で行う
- 操作と確定結果だけを送る
- 終了部屋を長く保持しない
- 画像と音を静的配信する

「サーバー費0円」を保証として表示しない。

無料枠内を目標にし、上限接近時に公開範囲と保存量を調整できるようにする。

## 23. GitHub運用

### 23.1 基本

- mainへ直接実装しない
- 1作業単位につき1ブランチ
- 1つの確認可能な成果物につき1Draft PR
- CI失敗中に別の機能を重ねない
- マージ前に、変更内容と確認結果をPR本文へ残す

### 23.2 PRの大きさ

細分化しすぎない。

適切な例：

- 12種類で一試合を完了できるルール基盤
- 24種類とCPUによるオフライン試作
- 世界4段階を含む戦闘画面
- 合言葉オンライン対戦
- 切断復帰と二重送信対策

避ける例：

- ボタン一つだけ
- 型一つだけ
- 空のフォルダだけ
- 後から必ず作り直す仮画面だけ

### 23.3 実機確認

実機でしか確認できない項目は、PRへ手順と結果を残す。

確認が難しい場合は、コード上の自動確認と、後続の実機確認を分けて明記する。

## 24. 優先リスク

| 優先度 | リスク | 検知方法 | 対応 |
|---|---|---|---|
| 最優先 | 最終評価に納得できない | 試合後質問、予想一致 | 表示と採点を再設計 |
| 最優先 | 世界が採点だけになる | 世界で行動を変えた率 | 世界反応とカード条件を変更 |
| 最優先 | オンラインが先行する | 工程の成果物確認 | 段階3まで通信着手禁止 |
| 高 | 破壊戦術が支配 | CPU方針別選定率 | 反動、対抗カード、減点調整 |
| 高 | 回復戦術が支配 | 最大ラウンド、回復使用率 | 費用、上限、効率調整 |
| 高 | 試合が長い | 時間分布 | 最大ラウンド、時計、カード調整 |
| 高 | 手札事故 | 使用不能手番 | 抑制、複数用途、山札枚数調整 |
| 高 | 切断で試合不能 | 復帰成功率 | 状態保存、再接続、猶予 |
| 中 | 端末で見切れる | 実機確認 | 情報の段階表示 |
| 中 | 演出量が膨らむ | 制作見積もり | 代表演出から作る |
| 中 | 名称と表現が既存作品に近い | 公開前レビュー | 固有神話、名称確認 |
| 中 | 無料枠を超える | 1試合使用量 | 保存削減、公開制限、料金判断 |

## 25. 一般公開を判断する条件

限定公開後に、次を確認する。

- 重大な進行停止がない
- 不正入力で状態を変更できない
- 切断復帰が実用になる
- 初回導入を完了できる
- 結果理由を理解できる
- 世界要素が実際の選択を変える
- 再戦が起きる
- 48種類と4世界で試合の変化がある
- 1試合の運用量と費用を把握している
- 名称、画像、音、フォントの確認が終わっている
- 利用規約と個人情報説明が用意されている

公開マッチングとレートは、一般公開とは別の判断にする。

## 26. 公開後の変更

### 26.1 ルール版

カードと採点を変更した場合、ルール版を更新する。

進行中の試合へ、途中から別の版を適用しない。

### 26.2 不具合時

- 新規ルーム作成を一時停止できる
- 進行中試合の扱いを表示できる
- 問題のあるカードを山札から外せる
- 前の安定版へ戻せる
- 不具合が起きたルール版を特定できる

### 26.3 バランス変更

一枚の勝率だけで変更しない。

次を合わせて見る。

- 使用率
- 解放率
- 抑制率
- 相手の対処可能性
- 世界への影響
- 初心者の理解
- 試合時間
- 特定の世界律だけで強すぎないか
