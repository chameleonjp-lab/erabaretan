# 選ばれたん：ゲームシニアエンジニアレビュー

- 文書状態：レビュー完了・次工程へ反映
- 更新日：2026-08-13
- 対象：`00_CURRENT_PLAN.md`、`07_TECHNICAL_ARCHITECTURE_V3.md`、`08_RULE_ENGINE_CONTRACT.md`、`09_PRODUCT_MANAGER_REVIEW.md`、`10_GAME_CREATOR_REVIEW.md`、`11_GAME_DESIGNER_REVIEW.md`

## 1. 結論

技術構成の骨格は維持してよい。

特に次の判断は妥当であり、今後も崩さない。

- 12種類の通信なしルール基盤から始める
- 画面とルール処理を分離する
- ルール処理を決定的にする
- カードへ自由なJavaScriptを書かない
- 乱数、ルール一式、カード一覧を版管理する
- オンラインでは対戦管理側が正しい状態を決める
- 1対戦部屋を1つのDurable Objectへ対応させる
- 完全状態をクライアントへ送らず、閲覧者ごとの公開状態を作る
- 切断、再送、古い操作、二重送信をルール外ではなく正式な設計対象にする
- ゴールデンリプレイと状態ハッシュで再現性を検査する

2026年8月13日時点でCloudflare公式資料を再確認したところ、Workers Static Assets、SQLite-backed Durable Objects、WebSocket Hibernationを組み合わせる基本構成は現在の提供機能と整合している。

一方、実装前に修正しないと後からルールエンジンを作り直しやすい問題がある。

最重要は次の七点である。

1. 技術設計V3とルール契約に処理順の食い違いがある
2. 自己犠牲の「支払い」が通常ダメージと区別されていない
3. 行動前予測を別ルール実装にすると本番処理とずれる
4. 選定優勢表示が秘密情報の漏えい経路になり得る
5. 記憶イベントの生成位置が未固定である
6. 「現在版と直前版だけ保持」では進行中試合を壊す可能性がある
7. バランス試験とルール正当性試験を分離する必要がある

したがって、次工程へ進んでよいが、実装開始前の技術契約へ本レビュー内容を反映する。

### 2.1 先攻最初の補充

ルール契約では、

- 両者へ7枚配る
- 先攻は最初の手番だけ補充しない
- 後攻は最初の手番から補充する

と固定されている。

一方、技術設計V3の`TURN_START`概要には単純に「カードを1枚引く」と記載されている。

実装はルール契約を正とする。

技術設計側も、

```text
if !(isFirstTurn && activePlayer == firstPlayer)
  draw 1
```

に相当する契約へ統一する。

### 2.2 効果キュー

ルール契約では、

```text
主カード効果
↓
防御・反応効果
↓
フィールド付随効果
↓
世界境界反応
↓
終了判定
```

が正式順序である。

技術設計V3には、防御・反応効果が省略された説明が残っている。

処理順はルール契約へ一本化する。

### 2.3 再発防止

同じ規則を複数文書へ手作業で重複記載し続けない。

実装開始後は、次を正本とする。

- ルール処理：`ruleset`とgame-coreの型
- カード：contentのカード定義
- 世界律：contentの世界律定義
- 通信：protocolのスキーマ

文書は、その正本を説明する位置付けへ寄せる。

## 3. 自己犠牲は通常ダメージと分離する

ゲームデザイナー工程では、

```text
自分の体力3〜5を支払う
→ 世界を5〜8再生
```

という自己犠牲再生を初期候補としている。

現在の共通効果命令には`DAMAGE_PLAYER`があるが、自己犠牲の支払いをこれで代用してはいけない。

理由は、通常ダメージには将来次のような処理が関わるためである。

- 防御
- シールド
- ダメージ軽減
- 反射
- 被ダメージ時反応
- 攻撃者情報

「体力を支払う」は攻撃を受けたこととは意味が違う。

### 3.1 追加する共通命令

初期候補として次を追加する。

```text
PAY_HP
```

最低限、次を持つ。

```text
amount
minimumHpAfterPayment
payer
```

最初の12種類では、自己犠牲による死亡を禁止するため、

```text
minimumHpAfterPayment = 1
```

を基本とする。

### 3.2 原子性

自己犠牲カードは、

1. 使用可能条件を確認
2. 支払い可能か確認
3. 体力を支払う
4. 世界再生を実行

の順とする。

支払いだけ成功して再生に失敗する中間状態を外へ公開しない。

カード使用全体を一つの正式な解決単位として処理する。

### 3.3 支払い失敗

体力不足なら、カード使用命令そのものを受理しない。

受理後に「支払えなかったので効果なし」とする設計は避ける。

## 4. 行動前予測は本番ルールをそのまま使う

ゲームデザイナー工程では、行動前に、

```text
世界79
星砕きを解放 → 世界73
次の境界75を通過
選定優勢 → 拮抗
```

のような予測表示を求めている。

このために画面側へ簡易計算式を別実装すると、必ず本番ルールとのずれが生じる。

### 4.1 推奨構造

概念上、次を用意する。

```text
previewCommand(currentState, command)
```

内部では本番と同じgame-coreを使用する。

- 元状態を変更しない
- 同じカード定義を使う
- 同じ効果順を使う
- 同じ世界境界判定を使う
- 同じ採点処理を使う

予測専用の別ルールエンジンは作らない。

### 4.2 乱数を含むカード

初期12種類では、行動結果へランダム対象を大量に入れない方針を維持する。

将来、結果が乱数で変わるカードを追加する場合、未来の乱数値を画面へ漏らしてはいけない。

その場合の予測は、確定部分だけを表示する。

例：

```text
世界損傷4は確定
対象はランダム
```

### 4.3 受入条件

同じ状態と操作について、

```text
previewの確定結果
実際にreduceした確定結果
```

が一致する自動試験を必須とする。

## 5. 選定優勢・拮抗・劣勢は公開情報だけから作る

試合中に正式な神の点数を常時大きく表示しない方針は妥当である。

一方、選定状況をサーバーだけが知る完全状態から直接算出すると、将来カード効果が増えたときに、相手の手札や山札などの秘密情報を間接的に漏らす危険がある。

### 5.1 安全な原則

選定傾向は、閲覧者へ既に公開してよい状態だけから計算する。

概念上、

```text
publicState = projectState(fullState, viewerId)
judgmentHint = calculateJudgmentHint(publicState)
```

とする。

現在の採点に必要な、

- 体力
- 生存ラウンド
- 世界損傷責任
- 実効世界再生
- 破界責任

は原則公開情報として扱えるため、初期版では成立させやすい。

### 5.2 不変条件試験

秘密情報だけを変え、公開状態を同じにした二つの完全状態について、

```text
judgmentHint(A) == judgmentHint(B)
```

になることを自動試験する。

これを秘密情報漏えい検査へ追加する。

### 5.3 三段階の境界

`優勢 / 拮抗 / 劣勢`の境界はUIの都合でgame-coreへ直書きしない。

`ruleset`または表示ルールとして版管理し、変更可能にする。

## 6. 記憶イベントは「事実」と「結果要約」を分ける

ゲームデザイナー工程では、

```text
WORLD_THRESHOLD_CROSSED
LARGEST_WORLD_DAMAGE_ACTION
LARGEST_EFFECTIVE_RESTORE_ACTION
SELECTION_LEAD_CHANGED
PLAYER_DEFEATED
WORLD_COLLAPSED
```

を候補としている。

ここでは二種類を分ける。

### 6.1 ルール中に発生する事実イベント

次はreduce中に決定的に生成できる。

```text
WORLD_THRESHOLD_CROSSED
PLAYER_DEFEATED
WORLD_COLLAPSED
WORLD_DAMAGED
WORLD_RESTORED
JUDGMENT_HINT_CHANGED
```

### 6.2 試合後に抽出する要約

次は試合全体の比較が必要である。

```text
LARGEST_WORLD_DAMAGE_ACTION
LARGEST_EFFECTIVE_RESTORE_ACTION
```

これらを毎手番の状態へ保存する必要はない。

終了後に正式イベント列から決定的に抽出する。

### 6.3 同じイベントから同じ要約を作る

結果画面、CPU試験、リプレイ再生のどこでも同じ要約になるよう、

```text
summarizeMatch(events)
```

を純粋な処理として持つ。

同点時の選択順も固定する。

例：

1. sequenceが早いもの
2. 同じならeventId固定順

## 7. 固定局面A〜Fを実装前の契約試験へ変換する

ゲームデザイナー工程の六局面は、そのまま自動試験へ変換できる。

### 7.1 Fixture形式

概念上、次を保存する。

```text
fixtureId
rulesetId
catalogHash
initialState
command
expectedEvents
expectedState
expectedStateHash
```

### 7.2 六局面

- A：大技で撃破できるが世界を傷つける
- B：世界76で損傷カードを持つ
- C：世界45、自分の体力8で自己犠牲再生を持つ
- D：相手の世界損傷責任が大きい
- E：世界0とプレイヤー撃破が同時に起こる
- F：第10ラウンドで両者生存

A〜Dは「ルールが正しい」だけでなく、UI予測用の入力としても使う。

E〜Fは終了処理と神の評価のゴールデンリプレイへ入れる。

### 7.3 人間の判断と自動試験を混同しない

自動試験は、処理が再現可能かを証明する。

「Aで本当に迷うか」は人間の試遊でしか証明できない。

同じFixtureを、

- 自動試験：結果の正当性
- 試遊：選択の迷い

の二用途に使う。

---

## 8. バランス値をコードへ直書きしない

ゲームデザイナー工程で未証明とされた値は、すべて検証用である。

- 生存ボーナス40
- 世界損傷係数-3
- 世界再生係数+2
- 破界責任25
- 世界境界75・50・25
- 世界損傷2〜8
- 自己犠牲体力3〜5
- 世界再生5〜8

これらをgame-coreの条件分岐へ散らさない。

### 8.1 rulesetへ集約する値

例：

```text
maxRounds
startingHp
worldMaxDurability
worldThresholds
survivalBonus
worldDamageScoreMultiplier
worldRestoreScoreMultiplier
worldCollapsePenalty
handLimit
```

### 8.2 カード定義へ置く値

例：

```text
playerDamage
worldDamage
worldRestore
hpCost
copiesInDeck
```

### 8.3 rulesetId

バランス変更で結果が変わる場合、新しい`rulesetId`または`catalogHash`を作る。

過去リプレイへ最新数値を上書きしない。

## 9. 「現在版と直前版だけ保持」を絶対条件にしない

技術設計V3では、配信物へ現在版と直前版のルール処理を含める方針になっている。

これは最小方針としては理解できるが、進行中試合の保護条件としては不十分である。

短時間に複数回配信した場合、まだ古いrulesetで動く部屋が残っている可能性がある。

### 9.1 正しい削除条件

ルール処理を削除できる条件を、

```text
「何世代前か」
```

ではなく、

```text
そのrulesetIdを参照する有効・復帰可能ルームが存在しない
```

で判断する。

初期運用で自動判定が重い場合は、安全側へ倒して複数世代保持してよい。

### 9.2 配信時の安全条件

最低限、

- 新規試合は最新rulesetだけを使用
- 進行中試合は開始時rulesetを使用
- 対応不能rulesetの部屋を読み込んだら勝敗を捏造せずSERVER_ABORT
- ruleset削除は通常配信と分ける

を守る。

## 10. Durable Objectの設計評価

1対戦部屋につき1Durable Objectとする方針は維持してよい。

2026年8月時点のCloudflare公式資料でも、新しいDurable ObjectではSQLite-backed storageが推奨され、WebSocket Hibernationによってアイドル時にオブジェクトをメモリから外しながら接続を維持できる。

このため、

- 1部屋を一つの調整単位にする
- 正しい試合状態は永続保存へ置く
- WebSocket attachmentには小さな接続情報だけ置く

という現行方針は妥当である。

### 10.1 保存は通知より先

現行の、

```text
新状態
受理操作
イベント
期限
```

を保存してからクライアントへ通知する順序を維持する。

通知後に保存へ失敗する構造は作らない。

### 10.2 Alarmは再実行されても壊れないようにする

期限処理には必ず`deadlineId`を持たせる。

同じ期限処理が再び呼ばれても、既に解決済みなら何もしない。

時間切れ既定行動も正式なcommandとして残す。

### 10.3 Hibernationを前提にメモリを信用しない

Durable Objectが再初期化された後でも、SQLiteとWebSocket attachmentから必要状態を復元できることを必須試験にする。

## 11. バランス試験と正当性試験を分離する

同じ自動対戦を一つの目的へ使わない。

### 11.1 正当性試験

目的：ルールが壊れていないこと。

- 同じseedと操作なら同じ最終ハッシュ
- 不変条件を破らない
- 世界境界が再発しない
- 二重commandが二度実行されない
- 秘密情報が漏れない
- Fixture A〜Fが期待結果になる

これはCIで常時実行する。

### 11.2 バランス試験

目的：狙ったゲーム展開が起きるかを見る。

記録候補：

- 平均・中央値ラウンド
- 世界75、50、25到達率
- 世界崩壊率
- 最大ラウンド率
- 解放率と抑制率
- 各カード使用率
- 戦闘勝者と神の選定者の一致率
- 先攻選定率
- 自己犠牲再生の使用率と使用後生存率

こちらは数値が変われば結果も変わってよい。

CIの「失敗」と直結させず、基準から大きく外れた場合にレビュー対象とする。

## 12. iPhone向け実装で守る境界

ゲームルールを画面のアニメーション完了へ依存させない。

### 12.1 正しい状態と表示状態を分ける

```text
authoritative state
↓
public projection
↓
presentation state
```

演出が途中でも、ルール上の状態は既に確定していてよい。

バックグラウンド復帰時は、途中アニメーションを無理に再現せず、最新状態へ追いつけるようにする。

### 12.2 Canvasの責任

現行どおり、カード操作や主要UIはHTML/CSSを中心にする。

Canvasは世界背景、亀裂、粒子などの演出へ限定する。

世界演出の負荷が高い場合でも、カード選択やタイマー操作を阻害しないことを優先する。

### 12.3 UI予測は端末で計算できる

通信前でも本人の現在公開状態と手札から確定できる範囲は、同じgame-coreをクライアントで動かして即時表示できる。

ただし最終的な受理可否と正式結果は対戦管理側が決める。

次のいずれかが未定義なら、game-core本実装へ進まない。

1. 12種類のカード定義と枚数

## 15. 敵対的レビュー工程への申し送り

次工程では、正常系ではなく、プレイヤーや通信が仕様の穴を突いた場合を検証する。

重点対象：

- 自己犠牲と回復を利用した点数稼ぎ
- 世界75・50・25直前で互いに損傷を避け続ける停滞
- 切断と時間切れを戦術として使う行為
- 同じcommandの再送、古いrevision、複数端末接続
- 選定優勢表示から秘密情報を推測できないか
- previewと正式結果の差を利用できないか
- ruleset更新途中の試合を壊せないか
- 世界崩壊と撃破を同時に起こして評価を不正利用できないか
- 大量イベントや効果連鎖による処理上限攻撃
- ルームコード探索や再接続資格の盗用

---

## 16. レビュー判定

**判定：条件付きで次工程へ進行可。**

現行技術構成を全面的に作り直す必要はない。

ただし、実装前に次を反映する。

- 技術設計V3とルール契約の不一致をルール契約へ統一
- `PAY_HP`を共通効果命令へ追加
- previewを本番game-coreの再利用で実装
- 選定傾向を公開情報だけから算出
- 記憶イベントを事実イベントと試合後要約へ分離
- Fixture A〜Fを契約試験へ変換
- バランス値をruleset/contentへ集約
- rulesetの保持期間を「世代数」ではなく進行中ルームで決める
- 正当性試験とバランス試験を分離

これらを満たせば、12種類のgame-coreを安全に実装できる状態へ進める。
