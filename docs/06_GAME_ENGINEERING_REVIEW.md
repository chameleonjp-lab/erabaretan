# 選ばれたん：ゲームエンジニアレビュー

- 文書状態：現行レビュー
- 対象：`04_GAME_PRODUCT_PLAN_V2.md`、`05_IMPLEMENTATION_AND_RELEASE_PLAN_V2.md`
- 更新日：2026-08-09
- 結論：企画方針は継続可。ただし、技術仕様を補完するまで本実装へ進まない

## 1. レビューの目的

本書は、現在のゲーム・商品計画と実装計画を、ゲームエンジン、通信、状態保存、再現性、iPhone対応、運用、安全性の観点から検証した結果をまとめる。

確認したいのは、単に「技術的に作れそうか」ではない。

- ルール追加で処理が破綻しないか
- 同じ試合を本当に再現できるか
- 秘密手札が漏れないか
- 二重送信や切断で状態が壊れないか
- 公開後の更新で進行中の試合が壊れないか
- iPhoneだけでも安定して遊べるか
- 問題が起きたとき、原因を特定できるか

を確認する。

---

## 2. 総合判定

現在のV2計画は、初期計画より大きく改善されている。

特に、次の判断は妥当である。

- 通信より先に、12種類のカードで面白さを確認する
- 画面、CPU、通信からルール処理を分ける
- 正式オンライン対戦では、プレイヤー端末を正しい状態の決定者にしない
- 1対戦部屋を一つのDurable Objectとして扱う
- 防御の連鎖を最初は1回へ制限する
- カードをデータと共通効果部品で構成する
- 切断復帰、二重送信、秘密情報、自動対戦を計画へ含める

一方で、現状は「良い方向を示した計画」であり、まだ「実装者が迷わず同じものを作れる仕様」にはなっていない。

**本実装への判定は条件付き保留**とする。

先に、次の最優先問題を解消する必要がある。

---

## 3. 最優先で直す問題

### 3.1 手番と補充の順序が文書内で食い違っている

ゲーム・商品計画では、手番の開始時にカードを1枚引く。

実装計画の基本処理順では、戦闘解決後に「補充と次の手番」が置かれている。

この違いは小さく見えるが、次へ影響する。

- 手札上限
- 山札切れ
- 引いた直後に使えるか
- 時間切れ時の手札
- リプレイ
- CPUの判断
- 先攻と後攻の有利不利

**修正判断：カード補充は手番開始時へ固定する。**

正式な状態遷移は次の順にする。

```text
TURN_START
↓
継続効果
↓
DRAW
↓
ACTION_SELECTION
↓
RESPONSE_SELECTION（必要な場合のみ）
↓
RESOLUTION
↓
TURN_END
```

カードを引いたあとに終了条件を確認する例外なども、別文書で固定する。

### 3.2 「同じ乱数なら再現できる」が、まだ成立していない

V2では、山札作成にWeb Crypto APIを使い、乱数の種を記録するとしている。

しかし、Web Crypto APIは予測しにくい乱数を作るための仕組みであり、そのままでは同じ試合を再生できない。

必要なのは次の分離である。

1. Web Crypto APIで、試合開始時の乱数の種を作る
2. ゲーム内では、版を固定した決定的な乱数生成器を使う
3. 乱数を使った順番と用途を固定する
4. 同じ種から同じ値が出る試験値を保存する

乱数生成器の種類を変えたら、同じ種でも結果が変わる。

そのため、`rngAlgorithmVersion`を試合へ保存する。

`Math.random()`、現在時刻、配列やオブジェクトの不定な順番を、ルール計算へ入れない。

### 3.3 カード効果の実行方法が曖昧

V2は「共通の効果部品を組み合わせ、特殊カードだけ専用処理を許可する」としている。

このままでは、カード追加のたびに専用処理が増え、次の問題が起きる。

- 処理順がカードごとに違う
- リプレイできないカードが混ざる
- CPUだけ挙動が違う
- 表示文章と実処理がずれる
- 専用処理同士で無限循環が起きる

最初の48種類までは、効果を小さな命令の組み合わせとして表す。

例：

```text
DAMAGE_PLAYER
BLOCK_DAMAGE
DAMAGE_WORLD
RESTORE_WORLD
DRAW_CARD
DISCARD_CARD
SET_FIELD
MODIFY_NEXT_ATTACK
```

これは、カード効果を決められた命令で表す方式である。実装では、判別可能な型の集合として定義する。

自由な文字列の実行、`eval`、カードデータ内のJavaScriptは使用しない。

専用処理は、共通命令では表せないことをレビューで確認した場合だけ追加する。

### 3.4 正しい状態の保存方法が決まっていない

V2には、対戦状態、イベント記録、リプレイがある。

しかし、次のどれを正しい情報として扱うかが曖昧である。

- 現在状態
- 受理した操作
- 発生イベント

すべてを別々に保存すると、途中で一つだけ失敗したときに食い違う。

**修正判断：実行時の正しい状態はスナップショットとし、受理操作とイベントを同じ保存処理で記録する。**

一つの操作を受理するときは、次を同じ原子的な保存単位で行う。

1. 操作IDを重複済みとして記録
2. 新しい状態を保存
3. 状態の版番号を増やす
4. 受理した操作を保存
5. 発生イベントを保存
6. 次の期限を保存

保存後に、各プレイヤーへ通知する。

通知に失敗しても、再接続時に保存済み状態へ戻れるようにする。

### 3.5 秘密情報を隠す責任境界が不足している

「相手の手札を送らない」という方針だけでは足りない。

実装中に完全な対戦状態を作り、そのあと画面側で隠す方法は採用しない。

対戦管理側に、閲覧者ごとの状態を作る専用処理を置く。

```text
projectState(fullState, viewer)
```

生成する状態は少なくとも次の三種類に分ける。

- プレイヤーA用
- プレイヤーB用
- 観戦者用（将来）

イベントにも公開範囲を持たせる。

```text
PUBLIC
PLAYER_A_ONLY
PLAYER_B_ONLY
SERVER_ONLY
```

完全状態を全員へ配信して、ブラウザ上で非表示にする実装は禁止する。

### 3.6 版番号を保存するだけでは、公開後の更新に耐えない

V2では、進行中の試合へ途中から別の版を適用しないとしている。

しかし、Cloudflare Workerを更新すると、休止から復帰したDurable Objectも新しいコードで動く。

試合に`ruleVersion`を保存しただけでは、古いルールを実行するコードが新しい配信物に残っていなければ再現できない。

**修正判断：進行中試合が参照するルール一式を`rulesetId`で固定し、配信物には現在版と直前版を同時に含める。**

- 新規試合は最新の`rulesetId`を使う
- 進行中試合は開始時の`rulesetId`を使い続ける
- 直前版は、進行中試合が存在し得る期間より長く保持する
- 過去版を削除する更新は、通常更新と分ける
- 保存形式の変更は、まず追加だけを行い、同じ更新で破壊的に削除しない

### 3.7 部屋コードと再接続トークンの安全性が不足している

短い数字だけの部屋コードを、そのままDurable Objectの識別子にすると、総当たりで入室を試されやすい。

最初の合言葉対戦では、次を固定する。

- 内部部屋ID：128ビット相当の予測しにくい値
- 手入力コード：推測しにくい英数字10文字程度
- 再接続トークン：128ビット以上
- 再接続トークンはURLへ入れない
- サーバーにはトークン本体ではなく検証用ハッシュを保存
- 復帰成功時にトークンを更新
- 同じプレイヤーの古い接続を無効化できる

6桁数字だけのコードは採用しない。

### 3.8 降参と切断を通常採点すると悪用できる

現在計画では、降参や切断猶予超過でも神の評価へ進む。

このままでは、次の悪用が起こり得る。

- 不利な評価になる直前に切断する
- 相手の正式な結果を変えるために降参する
- 短時間で評価や称号だけを得る

**修正判断：通常終了と不成立終了を分ける。**

```text
NORMAL
SURRENDER
DISCONNECT_FORFEIT
SERVER_ABORT
INVALID_MATCH
```

降参と切断敗北では、相手を対戦上の勝者として扱う。

ただし、通常の神評価分布、カード勝率、ランキング候補データには混ぜない。

サーバー障害では、両者の勝敗を確定しない。

### 3.9 山札の証明で保証できる範囲を明確にする

山札のハッシュを開始時に公開し、終了後に中身を公開すれば、開始後に山札を変更していないことは確認しやすくなる。

しかし、運営側が開始前に都合のよい山札を何度も作り直していないことまでは証明できない。

したがって、この機能を「山札が完全に公平である証明」と表現しない。

初期版では次の扱いにする。

- 山札作成は対戦管理側の暗号学的に安全な種を使う
- ハッシュは、試合途中の変更検知を補助する
- 公開ランキング導入前は、複雑な暗号配札を実装しない
- 将来、運営側も含めた公平性が必要なら、両プレイヤーの種を合わせる方式を別途検討する

### 3.10 Cloudflare構成が2026年時点の推奨と一部ずれている

V2は、画面をCloudflare Pages、通信をWorkerとして分けている。

現在のCloudflare公式資料では、新規の静的サイトや一体型アプリにはWorkers Static Assetsが推奨されている。

本作は画面と対戦入口を同じ配信単位にすると、次の利点がある。

- 画面と通信の版を一緒に更新できる
- 同一オリジンにできる
- CORS設定が減る
- プレビュー環境を分けやすい
- 静的ファイルとAPIの経路を一つの設定で管理できる

**修正判断：正式オンライン版は、Workers Static AssetsとWorkerを一体で配信する。**

オフライン試作までは通常のVite開発サーバーでよい。

## 4. 高優先で補う問題

### 4.1 状態遷移を列挙するだけでなく、受理可能な操作を表にする

各状態で、誰が、どの命令を送れるかを固定する。

例：

| 状態 | 行動者 | 受理する命令 |
|---|---|---|
| ACTION_SELECTION | 手番プレイヤー | PLAY_CARD、DISCARD、SURRENDER |
| RESPONSE_SELECTION | 防御側 | SELECT_DEFENSE、ACCEPT_DAMAGE、SURRENDER |
| RESOLUTION | なし | SURRENDER以外を拒否 |
| FINISHED | なし | REMATCH_REQUESTのみ |

画面表示ではなく、対戦管理側の状態で判定する。

### 4.2 一つの操作を二回処理しない仕組みに上限が必要

`commandId`を永久に保存すると、長期戦や攻撃で保存量が増え続ける。

- 同じ試合中の受理済み操作IDを保持する
- 試合終了後の保存期間を決める
- 1接続あたりの送信頻度と最大メッセージサイズを制限する
- 古い重複確認情報を、安全な範囲で整理する

### 4.3 CPUが秘密情報を見ないようにする

自動対戦では完全状態が必要だが、人間向けCPUに相手手札や山札順を渡すと、意図せず不正な強さになる。

CPUは、プレイヤー用に投影された状態と自分の手札だけを受け取る。

難易度を上げる場合も、秘密情報を与えるのではなく、探索量や評価の正確さで調整する。

### 4.4 時刻をルールへ混ぜない

`createdAt`は記録用の情報であり、ルール計算の入力にしない。

ゲーム内では、ラウンド、手番、順番、期限IDを使う。

残り時間は対戦管理側の締切時刻で判定し、端末の時計で勝敗を決めない。

### 4.5 Alarmは正確なタイマーとして扱わない

Alarmが指定時刻ぴったりに動く前提にしない。

- 最も近い期限を一つ保存する
- Alarm発火時に、現在状態と締切を再確認する
- 次の操作が届いたときも、先に期限超過を確認する
- 一度処理した期限を再実行しない

### 4.6 Hibernation中はメモリ状態が消える

接続にひも付く小さな情報だけをWebSocket attachmentへ保存する。

例：

- playerId
- sessionId
- connectionGeneration

手札、山札、体力、世界責任はSQLiteへ保存する。

WebSocket attachmentだけを再接続情報の正しい保存先にしない。

### 4.7 PRプレビューと本番の保存先を分ける

プレビューWorkerが本番のDurable Objectへ接続すると、試験で本番対戦を壊す。

環境を最低でも次に分ける。

```text
local
preview
production
```

各環境で、Worker名、Durable Object名前空間、秘密情報、計測先を分離する。

## 5. 実装時に禁止すること

- `Math.random()`をゲーム結果、ID、トークンへ使う
- 完全状態を全プレイヤーへ送り、画面側で隠す
- カードデータに実行可能なJavaScript文字列を入れる
- `eval`、`new Function`をカード処理へ使う
- 体力、世界耐久、得点を画面から直接変更する
- 受理前の操作を演出だけで確定扱いにする
- 同じ保存処理の途中で外部APIを呼ぶ
- 進行中の試合へ新しいカード数値を上書きする
- 本番とプレビューで同じDurable Object名前空間を使う
- 再接続トークン、山札、秘密手札を本番ログへ出す
- 初期版でService Workerによる強いキャッシュを入れる

Service Workerを初期版で避ける理由は、古い画面と新しい通信処理が混在しやすくなるためである。

## 6. 修正後の実装準備判定

次をすべて文書化した時点で、12種類のルール基盤へ進める。

1. 状態遷移と、各状態で受理する操作
2. カード効果命令の一覧
3. 乱数生成器の種類、版、試験値
4. カード定義IDとカード実体IDの区別
5. 世界境界を一度に複数越えた場合の順序
6. 同時死亡、世界0、最大ラウンドの終了順
7. 降参、切断、サーバー障害の結果種別
8. リプレイに必要な情報
9. プレイヤー別状態の投影規則
10. ルール更新中も進行中試合を続ける方法

これらは、`07_TECHNICAL_ARCHITECTURE_V3.md`と`08_RULE_ENGINE_CONTRACT.md`で補完する。

## 8. 最終判断

企画を中止する技術的理由はない。

1対1のターン制であり、1部屋1Durable Objectの構成は、処理量と整合性の面で適している。

ただし、品質を決めるのはCloudflareへの接続成功ではない。

> 同じ操作が必ず同じ結果になり、秘密が漏れず、切断後も正しい状態へ戻り、更新後も進行中の試合が壊れないこと。

これを満たすルール基盤を先に作る。

オンライン通信は、その基盤を別端末間で運ぶ手段として追加する。
