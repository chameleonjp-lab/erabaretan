# 選ばれたん：ルールエンジン契約

- 文書状態：実装前の必須契約
- 対象：最初の12種類から、48種類の限定公開版まで
- 更新日：2026-08-09
- 優先関係：ルール処理の詳細が他文書と食い違う場合は、本書を採用する

## 1. この文書の目的

本書は、企画文章を実装可能な規則へ変換する。

ゲームの見た目、通信方法、保存先が変わっても、次が一致するための契約である。

- 同じカードが同じ条件で同じ結果になる
- ブラウザ、CPU、自動対戦、オンライン対戦が同じ規則を使う
- 同時死亡や世界崩壊などの例外で実装者ごとの判断が分かれない
- 同じ乱数の種と操作列から同じ試合を再現できる
- 不正な操作や古い操作を、画面ではなくルール側で拒否できる

本書の数値は、初期検証用の`ruleset`として固定する。バランス調整で変更する場合は、進行中の試合へ上書きせず、新しい`rulesetId`を作る。

---

## 2. 初期ルール一式

最初の実装では、次を一つのルール一式として固定する。

| 項目 | 初期値 |
|---|---:|
| 対戦人数 | 2人 |
| 初期体力 | 30 |
| 世界耐久上限 | 100 |
| 初期世界耐久 | 100 |
| 初期手札 | 7枚 |
| 手札上限 | 9枚 |
| 最大ラウンド | 10 |
| 一手番の通常行動 | カード1枚、または手札1枚を捨てる |
| 防御・反応 | 一つの攻撃に対し最大1枚 |
| 自分の行動時間 | 18秒。オンライン時の検証値 |
| 防御判断時間 | 10秒。オンライン時の検証値 |
| 有効フィールド | 同時に1枚 |
| 世界境界 | 75、50、25、0 |
| 効果キュー上限 | 一解決につき32件 |

CPU練習では、時間制限を無効にできる。

### 2.1 最初の先攻補正

- 両者へ7枚ずつ配る。
- 先攻プレイヤーは、試合最初の手番だけ補充を行わない。
- 後攻プレイヤーは、最初の手番から通常どおり補充する。

最初の版では、画面に見えない「最初の2手番だけ致死ダメージを無効化する」といった特例を入れない。

序盤の即死は、先攻補正、初期体力、カード数値、一手番一行動によって防ぐ。これでも問題が残る場合は、明示的なルールとして新しい`rulesetId`へ追加する。

### 2.2 山札切れ

- 捨て札を山札へ戻さない。
- 山札が空なら補充を行わない。
- 山札切れだけでは試合を終了しない。
- 両者が行動可能なカードを持たず、状態が進まない場合は、最大ラウンドで終了する。

初期山札枚数は、通常の10ラウンドで山札切れが頻発しないように構成する。

## 3. 用語と識別子

### 3.1 カード定義とカード実体

同じ種類のカードが山札に複数存在するため、二つのIDを分ける。

```text
cardDefinitionId
cardInstanceId
```

**cardDefinitionId**

カードの種類を表す。

例：`attack.star-breaker.v1`

**cardInstanceId**

その試合の山札内に存在する一枚を表す。

同じ定義のカードが3枚あれば、異なる3個の実体IDを持つ。

### 3.2 主な識別子

```text
matchId
playerId
rulesetId
catalogHash
commandId
eventId
deadlineId
revision
sequence
turnSequence
roundNumber
```

- `revision`：正しい試合状態が変更されるたびに1増える。
- `sequence`：外部へ通知する出来事の順番。
- `turnSequence`：個々の手番へ付ける通し番号。
- `roundNumber`：先攻と後攻がそれぞれ一手番を行う組を表す。

IDに表示名やメールアドレスを使わない。

## 4. GameStateの概念構造

実際のTypeScript型は実装時に定義するが、正しい試合状態は少なくとも次を持つ。

```text
GameState
├─ rulesetId
├─ catalogHash
├─ engineVersion
├─ rngAlgorithmVersion
├─ shuffleAlgorithmVersion
├─ matchId
├─ revision
├─ phase
├─ roundNumber
├─ turnSequence
├─ activePlayerId
├─ respondingPlayerId?
├─ players
│  ├─ hitPoints
│  ├─ maxHitPoints
│  ├─ hand: cardInstanceId[]
│  ├─ worldDamageResponsibility
│  ├─ effectiveWorldRestore
│  ├─ survivedRoundCount
│  └─ statusEffects
├─ drawPile: cardInstanceId[]
├─ discardPile: cardInstanceId[]
├─ revealedCards: cardInstanceId[]
├─ cardInstances
├─ world
│  ├─ durability
│  ├─ maxDurability
│  ├─ triggeredThresholds
│  └─ worldLawId
├─ activeField?
├─ pendingAction?
├─ effectQueue
├─ terminalFlags
└─ randomConsumptionCount
```

接続状態、再接続トークン、表示名、実時間は、ゲーム結果を決める`GameState`へ入れない。

## 5. 正式な状態遷移

```text
SETUP
↓
TURN_START
↓
ACTION_SELECTION
├─ 応答が必要 → RESPONSE_SELECTION
└─ 応答不要   → RESOLUTION
↓
RESPONSE_SELECTION
↓
RESOLUTION
↓
TURN_END
├─ 継続 → TURN_START
└─ 終了 → JUDGMENT
↓
JUDGMENT
↓
FINISHED
```

### 5.1 SETUP

1. `rulesetId`、カード一覧、世界律を固定する。
2. 乱数の種を確定する。
3. 山札を作り、実体IDを割り当てる。
4. 両者へ7枚ずつ配る。
5. 先攻を決める。
6. 世界境界と世界律を公開する。
7. `TURN_START`へ進む。

### 5.2 TURN_START

1. 手番プレイヤーが生存していることを確認する。
2. 手番開始時の継続効果を処理する。
3. 先攻の最初の手番でなければ、カードを1枚引く。
4. 手札が9枚を超えた場合、超過破棄を要求する。
5. 必須の自動効果を解決する。
6. 終了条件を確認する。
7. 継続なら`ACTION_SELECTION`へ進む。

### 5.3 ACTION_SELECTION

手番プレイヤーは、次から一つを選ぶ。

- カードを使用する
- 使用可能なカードを抑制として使う
- 手札を1枚捨てて行動を終える
- 降参する

手札超過中は、通常行動より先に必要枚数を捨てる。

### 5.4 RESPONSE_SELECTION

防御側は、次から一つを選ぶ。

- 防御カードを1枚使う
- 反応カードを1枚使う
- ダメージを受ける
- 降参する

一つの攻撃に対する任意回答は最大1回である。

反応に対する再反応、反射に対する防御、反射に対する再反射は、最初の版では認めない。

### 5.5 RESOLUTION

- プレイヤーから新しい戦闘操作を受け付けない。
- 確定したカードと回答から効果キューを作る。
- キューを順番に処理する。
- 世界境界反応を処理する。
- 一つの解決単位を最後まで処理してから終了条件を確認する。

### 5.6 TURN_END

1. 手番終了時の効果を処理する。
2. 期限切れの一時効果を除く。
3. フィールドの終了時刻を確認する。
4. 後攻の手番が終わった場合、ラウンドを終了する。
5. 次の手番プレイヤーを決める。
6. 最大ラウンドを確認する。
7. 継続なら`TURN_START`へ進む。

### 5.7 JUDGMENT

通常終了の場合だけ、神の評価を正式に計算する。

降参、切断敗北、サーバー中止、不正な試合停止は、通常の神評価結果として扱わない。

## 6. 受理する命令

### 6.1 ルールエンジンへ渡す命令

```text
PLAY_CARD
DISCARD_FOR_ACTION
DISCARD_OVERFLOW
SELECT_RESPONSE
ACCEPT_DAMAGE
SURRENDER
TIMEOUT_DEFAULT_ACTION
```

オンラインの入室、再接続、再戦は、ルールエンジンの外側で扱う。

### 6.2 命令の共通情報

```text
commandId
playerId
expectedRevision
commandType
payload
```

ルールエンジンは、ダメージ値や得点をクライアントから受け取らない。

クライアントが送るのは、カード実体ID、使い方、対象、応答の選択だけである。

### 6.3 命令受理表

| phase | 送信者 | 受理する命令 |
|---|---|---|
| SETUP | なし | 外部の戦闘命令を拒否 |
| TURN_START | なし | 外部の戦闘命令を拒否 |
| ACTION_SELECTION | 手番プレイヤー | PLAY_CARD、DISCARD_FOR_ACTION、DISCARD_OVERFLOW、SURRENDER |
| ACTION_SELECTION | 相手 | SURRENDERのみ |
| RESPONSE_SELECTION | 防御側 | SELECT_RESPONSE、ACCEPT_DAMAGE、SURRENDER |
| RESPONSE_SELECTION | 攻撃側 | SURRENDERのみ |
| RESOLUTION | 両者 | SURRENDERのみ。処理中の即時割り込みには使わず、解決後に適用 |
| TURN_END | なし | 外部の戦闘命令を拒否 |
| JUDGMENT | なし | 外部の戦闘命令を拒否 |
| FINISHED | なし | 戦闘命令を拒否 |

古い`expectedRevision`の命令は、危険な自動再適用を行わず拒否する。

同じ`commandId`の再送は、状態を二度変更せず、最初の受理結果を返す。

## 7. カード定義の契約

### 7.1 必須項目

```text
cardDefinitionId
cardVersion
displayName
role
worldImpactType
playModes
responseModes
targetRule
conditions
effects
copiesInDeck
introducedRulesetId
```

### 7.2 戦闘上の役割

```text
ATTACK
DEFENSE
INTERVENTION
FIELD
```

### 7.3 世界への影響

```text
RESTORE
NEUTRAL
DAMAGE
```

最初の版では、一枚のカードへ`DAMAGE`と`RESTORE`を同時に持たせない。

世界を壊してから同じカードで直すような分かりにくい責任計算を避けるためである。

### 7.4 使用方法

```text
RELEASE
RESTRAIN
RESPONSE
```

すべてのカードが三つを持つ必要はない。

世界損傷が大きいカードは、原則として`RESTRAIN`を持つ。

## 8. 共通効果命令

最初の候補を次に固定する。

```text
DAMAGE_PLAYER
HEAL_PLAYER
ADD_SHIELD
REDUCE_INCOMING_DAMAGE
REFLECT_DAMAGE
DRAW_CARD
DISCARD_CARD
DAMAGE_WORLD
RESTORE_WORLD
SET_FIELD
CLEAR_FIELD
MODIFY_STAT_UNTIL_TURN_END
MODIFY_NEXT_ACTION
REVEAL_PUBLIC_INFORMATION
ADD_SCORE_MODIFIER
```

### 8.1 共通原則

共通効果命令の正式な入力型、結果型、責任、拒否条件は、[共通効果命令の正式型 V1](19_COMMON_EFFECT_COMMANDS_ALPHA_12_V1.md)を正本とする。

- 効果命令は型で区別する。
- 自由なJavaScript文字列をカードデータへ入れない。
- `eval`と`new Function`を使わない。
- カード定義内の命令は、記載順に処理する。
- すべて整数で扱う。
- 数値の上下限を命令ごとに定める。

### 8.2 ダメージ

基本順序：

```text
基礎ダメージ
↓
攻撃側の修正
↓
フィールドと世界律の修正
↓
防御側の軽減
↓
0未満を0へ補正
↓
体力へ適用
```

防御値が攻撃値を超えても、余剰防御を次の攻撃へ持ち越さない。

### 8.3 反射

- 反射は、元攻撃の解決内で発生する別の`DAMAGE_PLAYER`として扱う。
- 最初の版では、反射ダメージへ任意回答を行えない。
- 反射から再び反射を発生させない。
- 反射で攻撃者が体力0になっても、現在の必須解決を最後まで行う。

### 8.4 回復

- 最大体力を超えた分は切り捨てる。
- 体力0になったプレイヤーを、同じ解決中の通常回復で復活させない。
- 復活カードは最初の版へ入れない。

### 8.5 世界再生

実効世界再生は、実際に増えた世界耐久だけを記録する。

```text
実効世界再生
= min(再生要求値, 世界耐久上限 - 再生前世界耐久)
```

世界耐久が100なら、再生要求値があっても実効世界再生は0である。

### 8.6 フィールド

- 同時に一つだけ有効。
- 新しいフィールドを置くと、古いフィールドを直ちに終了する。
- 最初の版では、古いフィールドの終了時効果を発生させない。
- 持続時間は曖昧な「2ラウンド」ではなく、絶対的な`expiresAfterTurnSequence`で保存する。
- フィールドの責任者を保存する。

## 9. 効果キュー

### 9.1 基本順序

```text
主カード効果
↓
防御・反応効果
↓
フィールドの付随効果
↓
世界境界反応
↓
終了判定
```

カード定義から作った効果命令は、先に入ったものから処理する。

### 9.2 上限

一つの解決単位で処理できる効果命令は32件までとする。

上限を超えた場合は、残りを黙って捨てない。

試合を`INVALID_MATCH`として停止し、次を記録する。

- rulesetId
- catalogHash
- cardDefinitionId
- commandId
- 直前までの効果キュー
- 状態ハッシュ

### 9.3 専用処理

共通命令で表せない効果だけ、登録済み専用処理を使える。

専用処理には次を必須とする。

- `specialEffectId`
- 入力型
- 出力型
- 決定性
- 外部入出力を行わないこと
- 単体試験
- ゴールデンリプレイ

最初の12種類では、専用処理を使用しない。

## 10. 世界境界

### 10.1 発生条件

世界耐久が、未発生の境界を上から下へ越えたときに発生する。

```text
変更前 > 境界値
かつ
変更後 <= 境界値
```

一度発生した境界は、世界が回復して再び下がっても発生しない。

### 10.2 一度に複数越えた場合

世界耐久が80から20になった場合、次の順で一度ずつ処理する。

```text
75
↓
50
↓
25
```

### 10.3 発生時点と解決時点

境界を越えた時点で、対象の反応をキューへ追加する。

主カードと必須の付随効果を処理したあと、境界反応を解決する。

キューへ入ったあとに世界が回復して境界より上へ戻っても、反応は取り消さない。

### 10.4 境界反応がさらに世界を傷つける場合

新しく越えた未発生境界を、既存の境界反応の後ろへ追加する。

すでに発生済みの境界は追加しない。

### 10.5 世界0

世界耐久は0未満にならない。

世界0になっても、現在の必須効果と境界反応を途中で打ち切らない。

解決後に通常終了へ進み、最後に世界0へ到達させた責任者へ破界責任を記録する。

一つの解決で複数の世界損傷が0へ到達させた場合、最初に0へ到達させた効果の責任者を破界責任者とする。

## 11. 世界責任

### 11.1 世界損傷

実際に減った世界耐久を、効果の責任者へ記録する。

```text
実効世界損傷
= min(損傷要求値, 損傷前世界耐久)
```

世界耐久が0のあとに発生した追加損傷は、世界耐久をさらに減らさない。

ただし、カード文章で別の個人責任を課す場合は、`ADD_SCORE_MODIFIER`として明示する。

### 11.2 世界再生

実際に増えた量だけを、効果の責任者へ記録する。

他人が壊した分を回復しても、自分の過去の世界損傷は消えない。

### 11.3 フィールドの責任

フィールドが継続的に世界へ影響する場合、フィールドを使ったプレイヤーへ帰属する。

フィールドが別のカードの損傷を増幅した場合は、初期版では増幅分も元カード使用者へ帰属する。

責任の分割が必要なカードは、カード文章と試験で明示する。

## 12. ラウンドと生存

### 12.1 ラウンド

1ラウンドは、先攻と後攻がそれぞれ一回ずつ手番を行う組である。

ラウンド途中に試合が終了した場合、そのラウンドは完了していない。

### 12.2 生存ラウンド数

各プレイヤーの`survivedRoundCount`は、体力が1以上の状態で迎えたラウンド開始ごとに1増える。

- 両者はラウンド1開始時に1を得る。
- 次ラウンド開始時に体力0の者は増えない。
- ラウンド途中で死亡しても、そのラウンド開始時に得た値は失わない。

この定義により、先攻と後攻で「死亡した手番の位置」だけによる不公平な差を作りにくくする。

### 12.3 最大ラウンド

後攻の第10ラウンド手番を解決し、`TURN_END`へ到達した時点で終了する。

第10ラウンド途中に体力0または世界0となった場合は、その通常終了原因を優先して記録する。

## 13. 正常終了の判定

### 13.1 終了確認の時点

- 一つの解決単位と、そこから発生した必須反応の終了後
- TURN_STARTの必須効果終了後
- TURN_ENDの必須効果終了後

任意回答の途中では、体力0だけを理由に処理を中断しない。

### 13.2 正常終了で保存する原因

一つだけの文字列へ情報を潰さず、次を保存する。

```text
worldCollapsed: boolean
defeatedPlayerIds: playerId[]
maxRoundsReached: boolean
```

画面へ出す主原因の優先順は次とする。

1. 世界崩壊
2. プレイヤー撃破
3. 最大ラウンド

ただし、同時に起きた事実はすべて結果詳細へ表示できる。

### 13.3 同時死亡

両者の体力が0なら、戦闘結果は引き分けとする。

神の評価は通常どおり計算する。

神の評価が同点なら、神の選定も引き分けとする。

### 13.4 世界0と死亡が同時に起きた場合

- 世界崩壊と撃破の両方を記録する。
- 破界責任を記録する。
- 生存者は、必須効果終了後に体力1以上の者とする。
- 神の評価を通常どおり計算する。

### 13.5 最大ラウンド

両者の体力が1以上なら、残り体力が多い者を戦闘勝者とする。

同値なら戦闘は引き分けである。

神の選定は、神の評価で別に決める。

## 14. 神の評価

### 14.1 初期式

```text
生存評価
= survivedRoundCount × 2
+ 終了時体力
+ 生存ボーナス

生存ボーナス
= 通常終了時に体力1以上なら40
= それ以外は0

世界評価
= 実効世界再生 × 2
- 個人世界損傷 × 3
- 破界責任

破界責任
= 破界責任者なら25
= それ以外は0

神の評価
= 生存評価 + 世界評価
```

### 14.2 終了時体力

0未満を0として扱う。

最大体力を超えない。

### 14.3 同点

同点は引き分けとする。

乱数、入力速度、先攻、通信時間で同点を崩さない。

### 14.4 暫定評価

暫定評価は、現在状態で今すぐ正常終了したと仮定した参考値として計算する。

暫定評価は勝敗を確定しない。

画面が送った暫定評価をルール側で信用しない。

---

## 15. 通常以外の終了

```text
NORMAL
SURRENDER
DISCONNECT_FORFEIT
SERVER_ABORT
INVALID_MATCH
```

### 15.1 SURRENDER

- 降参した側を対戦敗北とする。
- 相手を対戦勝者とする。
- 正式な神の選定者を決めない。
- 通常の選定率、カード勝率、世界崩壊率へ含めない。
- 行動履歴と参考内訳は表示できる。

### 15.2 DISCONNECT_FORFEIT

- 切断猶予を超えた側を対戦敗北とする。
- 相手を対戦勝者とする。
- 正式な神の選定者を決めない。
- 通常のゲームバランス統計へ含めない。
- 通信品質の統計へ含める。

### 15.3 SERVER_ABORT

- 両者の勝敗を確定しない。
- 正式な神の評価を出さない。
- 利用者へサーバー側の中止であることを表示する。

### 15.4 INVALID_MATCH

- ルール処理上限、保存不整合、未定義状態などで使用する。
- 勝敗を確定しない。
- 通常統計へ含めない。
- 調査に必要な版、操作、状態ハッシュを記録する。

## 16. 時間切れ

### 16.1 ACTION_SELECTION

通常行動の時間切れでは、次の安全な既定行動を行う。

1. 手札超過中なら、決定的な規則で1枚捨てる。
2. 通常状態なら、手札を1枚捨てて手番を終える。
3. 手札が0なら、何もせず手番を終える。

自動で世界損傷カードを解放しない。

決定的な自動破棄は、最も新しく引いたカードを第一候補とし、同条件なら`cardInstanceId`の固定順で決める。

### 16.2 RESPONSE_SELECTION

時間切れでは、防御や反応を自動使用せず、`ACCEPT_DAMAGE`として処理する。

### 16.3 連続時間切れ

初期合言葉対戦では、同一プレイヤーが連続3回時間切れした場合、切断敗北と同じ扱いへ進める案を初期値とする。

この値は、通信切断と操作放置を区別した計測後に調整する。

---

## 17. 決定的乱数

### 17.1 種

試合開始時にWeb Crypto APIで予測しにくい種を作る。

ゲーム内では、その種を版固定した決定的乱数生成器へ渡す。

### 17.2 禁止入力

ルール計算へ次を入れない。

- `Math.random()`
- `Date.now()`
- 端末の時刻
- 描画フレーム数
- ネットワーク到着時刻
- 配列へ変換していないオブジェクトキーの偶然の順序

### 17.3 保存

```text
seed
rngAlgorithmVersion
shuffleAlgorithmVersion
randomConsumptionCount
```

### 17.4 乱数消費

乱数を使う処理ごとに、用途を固定する。

例：

```text
SHUFFLE_DECK
SELECT_FIRST_PLAYER
RANDOM_TARGET
```

カード文章の表示や演出は、ゲーム結果用の乱数を消費しない。

演出用乱数は別の種を使う。

## 18. リプレイ契約

### 18.1 必須情報

```text
replayFormatVersion
engineVersion
rulesetId
catalogHash
rngAlgorithmVersion
shuffleAlgorithmVersion
seed
initialPlayerOrder
acceptedCommands
expectedFinalStateHash
expectedEndKind
```

### 18.2 受理操作

受理された命令だけを記録する。

拒否された不正命令や重複再送は、監査ログへ残せるが、試合再現の入力へ含めない。

時間切れの既定行動は、サーバーが作った正式な命令として操作列へ含める。

### 18.3 状態ハッシュ

状態ハッシュは、安定したキー順で直列化したゲーム状態から作る。

次はハッシュ対象から除く。

- 実時間
- WebSocket状態
- 再接続トークン
- 表示名
- 調査用ログID

状態ハッシュは、再現結果の一致確認に使う。秘密情報の安全を証明するものではない。

### 18.4 保証範囲

初期版で長期的な利用者向けリプレイ互換を保証しない。

開発、試験、不具合調査では、現在版と直前版のルールで再生できることを保証する。

長期保存する公開リプレイは、別機能として設計する。

## 19. 公開状態の契約

完全状態をそのままクライアントへ送らない。

```text
projectState(fullState, viewerId)
```

### 19.1 全員へ公開

- 両者の体力と最大体力
- 両者の手札枚数
- 世界耐久
- 個人別の世界損傷と実効世界再生
- 世界律
- 現在のフィールド
- 発生済み世界境界
- ラウンド、手番、期限
- 公開されたカード
- 暫定評価の公開部分

### 19.2 本人だけへ公開

- 自分の手札内容
- 自分が選べる応答候補
- 自分の未確定選択

### 19.3 非公開

- 相手の手札内容
- 未配布の山札順
- 未使用の乱数状態
- 山札証明のSalt
- 再接続トークンとハッシュ

### 19.4 イベントの公開範囲

```text
PUBLIC
PLAYER_1_ONLY
PLAYER_2_ONLY
SERVER_ONLY
```

カードを引いた事実は公開できるが、引いたカードの内容は本人だけへ送る。

## 20. 不変条件

どの正しい操作列でも、次を破ってはならない。

1. 体力は0から最大体力の範囲にある。
2. 世界耐久は0から上限の範囲にある。
3. 同じカード実体は、山札、手札、捨て札、場の複数箇所へ同時に存在しない。
4. すべてのカード実体数の合計が、試合開始時の総数と一致する。
5. 発生済み世界境界は再発しない。
6. `revision`は受理操作ごとに増え、減らない。
7. 同じ`commandId`で二度状態が変わらない。
8. `FINISHED`後にゲーム状態が変わらない。
9. 公開状態へ秘密手札と山札順が混ざらない。
10. 世界責任台帳の合計が、実際の世界変化と一致する。
11. 効果キューが上限を超えて正常続行しない。
12. すべてのルール数値は整数である。
13. 同じリプレイ入力から同じ状態ハッシュが得られる。

- 中立攻撃

- 通常撃破

## 23. 変更管理

次の変更は、新しい`rulesetId`を必要とする。

- 初期体力、手札、最大ラウンド
- 補充順
- 状態遷移
- 効果命令の意味
- カード数値と枚数
- 世界律
- 採点式
- 終了条件
- 時間切れの既定行動

表示文、画像、音だけの変更は、ゲーム結果が変わらない限り`clientBuildId`だけを更新できる。

ただし、カード説明文が処理内容と食い違う修正は、影響を確認してカード版を更新する。

## 24. 完了条件

本書を実装へ渡せる状態は、次を満たすときである。

- 12種類のカードが共通効果命令だけで表せる
- 状態遷移と命令受理表に抜けがない
- 世界境界と同時終了の例が手計算できる
- 神の評価を同じ入力から再計算できる
- ゴールデン試合3件が確定している
- 決定的乱数の試験値が決まっている
- 公開状態と秘密状態を区別できる
- 変更時に`rulesetId`を上げる範囲が分かる

この条件を満たした後、12種類の純粋なルール基盤を実装する。
